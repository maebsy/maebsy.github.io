## 概要

`ai-gitgen` は、Git リポジトリのステージ済みの変更（ステージされた変更がない場合は作業ツリーの変更）を読み取り、Conventional Commits 形式のコミットメッセージ、または *Why*・*What*・*How to Test* の各セクションを持つ PR のタイトルと本文の下書きを作成します。OpenAI、Anthropic、Gemini の REST API に対応しています。学習課題として 1人で開発したもので、API を呼び出すこと自体よりも、出力の品質・コスト・情報漏えいをコードで制御することに重点を置きました。

## 背景と課題

diff を外部 API に送る際には、実務上 3つの問題があります。

1. **情報漏えい。** diff には API キーやデータベースのパスワード、個人情報が含まれていることが多く、一度送信した値は取り消せません。
2. **形式のずれ。** 件名を 72文字以内と指示しても、90文字で返ってきたり、セクションが抜けたりすることがあります。
3. **コスト。** 形式が正しくなるまで再生成を繰り返すと、API 呼び出しが増え続けます。

## 構成

```text
git status / git diff ─▶ セーフモード（マスキング・除外・上限）─▶ プロンプト ─▶ LLM REST 呼び出し
        ─▶ 検証・後処理 ─┬─▶ 出力・.git/ai-gitgen/ に保存
                         └─ 内容が欠けている場合のみ 1回再生成
```

| モジュール | 役割 | 依存しないもの |
| --- | --- | --- |
| `git.py` | リポジトリの確認、status と diff の収集 | AI、プロンプト |
| `safety.py` | マスキング、ファイル除外、送信量の上限 | Git、AI |
| `prompts.py` | 規約・文脈・diff からプロンプトを構成 | API、検証 |
| `llm/` | プロバイダ別の REST リクエスト、エラーの変換 | Git、プロンプトの内容 |
| `drafts.py` | JSON の解釈、後処理、ルール検証、レンダリング | API、Git |
| `app.py` | 処理順序の制御と呼び出し回数の上限 | — |

依存の方向が守られているかは、テスト（`test_structure.py`）で確認しています。

## 設計・実装の判断

リポジトリの `docs/design.md` に設計判断の記録を残しています。主なものは次のとおりです。

| 判断 | 代替案 | 理由 |
| --- | --- | --- |
| モデルには JSON で内容のみを出力させ、Markdown はコードで生成 | モデルに Markdown を直接書かせる | 形式の保証をコード側に移し、有料の再生成を減らすため |
| 長さや形式はコードで確実に修正し、内容が欠けた場合のみ再生成 | ルール違反のたびに再生成 | コードで直せるものは無料で直すため |
| 標準ライブラリの `urllib` を使用 | 公式 SDK 3種 | REST の流れがコード上で明確になり、依存が少なく、プロバイダの追加も容易なため |
| セーフモードを既定で有効化 | オプションでのみ有効化 | 機密情報は一度漏れると取り返しがつかないため |
| 送信行数の上限をファイルごとに均等に配分 | diff の先頭から切り詰める | 大きなファイル 1つが上限を使い切り、設定ファイルの変更がまるごと抜け落ちる問題を見つけたため |
| ステージ済みの変更を優先して収集 | 常に作業ツリー全体を対象 | コミットメッセージは実際にコミットされる内容を説明すべきため |

**セーフモード。** リクエストを組み立てる前に、14種類の正規表現ルールで、各種 API キー（OpenAI、Anthropic、GitHub、AWS、Google、Slack）、JWT、秘密鍵、URL に含まれる認証情報、`password=` の値、メールアドレス、韓国の住民登録番号、電話番号、Luhn チェックを通るカード番号をマスキングします。`.env` や `*.pem` など約 20種類の機密ファイルは送信対象から除外し、送信量は 10ファイル・200行までに制限しています。`--dry-run` を使うと、API を呼び出さずに送信内容をそのまま確認できます。

**エラー処理。** スタックトレースの代わりに、原因と対処方法を表示します。終了コードは、設定エラー（2）、Git エラー（3）、API エラー（4）、再生成後も形式要件を満たさない場合（5）に分けています。

## 検証と成果

- **テスト。** `python -m pytest -q` → **125件成功、サブテスト 45件成功**（2026年11月25日に再実行、Python 3.12・Windows）。偽のプロバイダとローカル HTTP サーバーを使うため、ネットワーク・API キー・費用なしで実行できます。
- **CI。** GitHub Actions で、Ubuntu・Windows × Python 3.10〜3.14 の組み合わせでテストを実行し、セーフモードの dry-run デモと、Windows 上での PowerShell の構文チェック・スモークテストも行っています。
- **実行ログ。** `docs/evidence/` に実際の CLI 出力を 17種類保存しています（API キー未設定、変更なし、temperature やトークン上限の比較、ネットワーク・認証エラー、応答の途中切れなど）。
- **使用量の実測。** 197行の diff に対して、コミットメッセージ 1回の生成で入力約 3,750トークン、出力 120〜220トークンでした（当時使用したモデルでの値を README に記録）。

README には、そのままでは使えない PR 下書きの例もあえて残しています。テスト手順に `pytest` と書かれていますが、対象プロジェクトでは pytest を使っていません。このツールが生成するのはあくまで下書きであり、レビューが必要であることを示すためです。

## 再現手順

Python 3.10 以上、Git、[uv](https://docs.astral.sh/uv/) が必要です。

```bash
git clone https://github.com/maebsy/ai-gitgen.git
cd ai-gitgen
uv sync --group dev
uv run pytest                       # API キー不要
uv run ai-gitgen commit --dry-run   # 送信されるプロンプトを表示
```

実際に生成するには、環境変数 `AI_API_KEY` が必要です。キーは環境変数、または Git の管理対象外である `.env` からのみ読み込みます。

## 制約と改善点

- 正規表現によるマスキングは既知の形式しか検出できません。そもそも機密情報をリポジトリに含めないことが前提です。
- 上限を超える diff はファイル名のみの送信になるため、大規模な変更では下書きの精度が下がります。
- PyPI では配布しておらず、インストールはソースからのみです。
