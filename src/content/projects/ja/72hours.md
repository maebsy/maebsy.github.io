## 概要

72hours は、コディセイ AI ハッカソン 2026 において 5名のチームで 4日間かけて開発したサービスです。AI コーディングツールで小規模なサービスを素早く作れる一方、セキュリティレビューには慣れていない開発者を対象としています。公開 GitHub リポジトリの URL を入力すると、複数のスキャナを実行して結果を正規化し、ローカルで動作する LLM が各検出項目を解説します。さらに、レビュー済みの修正指示を MCP 経由で利用者自身のコーディングエージェントに渡し、修正の push 後に再検査します。

このページでは、私が担当した部分を中心に説明します。他のメンバーの担当部分は、関係する箇所で明記しています。

## 背景と課題

AI ツールで生成されたコードには、データベースの管理者キーがソースに含まれている、認証のない書き込み API がある、行レベルセキュリティ（RLS）が無効なテーブルがある、といった問題がよく見られます。対象となる開発者はスキャナを実行することはできても、次の 3点で行き詰まります。警告が多すぎて優先順位がわからないこと、修正方法がわからないこと、そして修正が本当に効いたのかを確認する手段がないことです。

大会期間中の制約は次のとおりでした。

- 推論に使える GPU は L4 1枚のみで、検出項目 1件あたりの LLM 処理には数分かかる。
- リスクレベルとシェルコマンドは再現可能でなければならず、言語モデルに決めさせない。
- サービス側から利用者のコードを直接変更しない。修正は利用者の環境で、利用者の許可を得て行う。

## 構成

```text
ブラウザ ── Next.js ── FastAPI ──┬── 検査エンジン ── Opengrep / OSV-Scanner / Gitleaks / 設定チェック
                                 ├── LLM パイプライン（vLLM, Qwen3.8-27B）：文脈分析 → Blue → Red
                                 └── 実行検証サンドボックス（Docker、デモ用ターゲットのみ）
利用者のコーディングエージェント ── リモート MCP サーバー ── FastAPI
```

構成はリポジトリの README に基づいています。検査エンジンは 1回の検査につき 1つの JSON を出力し、LLM パイプラインがそれを受け取ります。MCP サーバーは、検査結果と承認済みの修正指示を Claude Code や Codex などのエージェントに提供します。

## 設計・実装の判断

**複数スキャナの結果を 1つの形式に統一。** スキャナごとに出力形式が異なるため、エンジンはスキャナを並列実行し、すべての結果を共通スキーマに変換したうえで、行番号に依存しないフィンガープリントを付与します。これにより、編集でコードの位置が変わっても同じ問題として識別できます。2回の検査結果を比較すると、「新規」「継続」「解決」「確認不可」の 4状態に分類されます。「確認不可」を設けたのは、スキャナの失敗を「解決」と誤って報告しないためです。

**判定はコード、説明はモデル。** リスクの判定は、文脈のシグナルと脅威情報（CISA KEV、FIRST EPSS）に CISA SSVC の決定表を適用するコードが行います。シェルコマンドも OS ごとに検証済みのテンプレートからのみ生成します。モデルが担当するのは説明文と修正指示の作成です。これにより、同じ入力に対しては常に同じ優先度になり、モデルが存在しないコマンドを作り出すこともありません。

**Blue が書き、Red がレビューする。** 「Blue」が説明と修正指示を作成し、「Red」が攻撃の回避可能性、機能の破損、漏れの観点からレビューします。書き直しの回数には上限があり、通過しなかった項目は手動確認の対象として表示します。Red の「pass」はあくまでモデルの判断であり、証明ではありません。攻撃が実際に防がれるかどうかは、デモ用ターゲットに対する別の実行検証でのみ判定します。

**修正はサーバーではなく MCP を通じて。** MCP サーバーが転送するのは、Red のレビューを通過し、かつ最新の検査結果のフィンガープリントと一致する修正指示だけです。検証の実行中に同じ依頼が重複して送られた場合は受け付けません。コードの編集は利用者のエージェントがローカルで行い、push するかどうかは利用者が決めます。

**リクエストを取りこぼさないデプロイ。** `main` からの自動デプロイを構築し、ジョブキュー、処理中ジョブのドレイン、中断されたリリースの次回実行時のロールバックを実装しました。

## 検証と成果

以下はリポジトリに記録されている結果で、記載した対象にのみ当てはまります。

- **デモ用リポジトリ 1件での検出結果。** デモ用に意図的に脆弱に作成したサイト（キーはすべて偽物）[`cafe-order-demo`](https://github.com/maebsy/cafe-order-demo) の正解リストに対し、検出 15件、見逃し 1件、誤検出 0件でした。見逃したのは `// nosemgrep` コメントで隠された SQL インジェクションです。一般的な検出率を示すものではありません。
- **デモ用ターゲットでの修正前後の実行検証。** SQL インジェクションと反射型 XSS は、修正前はいずれも成功し、修正後は防がれました。機能テストは修正前後ともに成功し、サンドボックスの隔離に関する 4項目も確認しています（ローカル Docker、2026年10月31日）。
- **レビューで実際の不具合を発見。** #141 では、検証の途中でツールを再度呼び出すとジョブが重複登録される問題と、別の PR と統合した際に発生する `TypeError` をレビュアーが再現しました。いずれも回帰テストを追加して修正したうえでマージしています。
- **CI。** 関連ファイルが変更された PR ごとに、バックエンド、フロントエンド、検査エンジン（実スキャナを実行）、MCP、デプロイのテストを GitHub Actions で実行しました。

## 再現手順

リポジトリの README に、Docker を使わないローカル環境の構築手順があります。必要なのは Python 3.12、Node.js 24、3種類のスキャナで、任意で vLLM と 24GB クラスの GPU を用意します。GPU がなくても、エンジンの検査結果とルールベースの説明は利用できます。

```bash
git clone https://github.com/maebsy/YMCA-hackathon-2026.git
cd YMCA-hackathon-2026
cp .env.example .env
python -m security_engine doctor   # インストール済みのスキャナを確認
```

大会期間中に使用した公開デモの URL は、現在は稼働していません（2026年11月25日確認）。

## 制約と改善点

- 検査対象は公開リポジトリのデフォルトブランチのみで、機密情報は現在のファイルだけを確認し、Git の履歴は対象外です。
- L4 GPU 1枚では検出項目 1件あたり数分かかるため、LLM による解説はリスク上位 5件に限っています。
- 実行検証はデモ用ターゲットのみに対応しており、利用者のリポジトリには対応していません。
- 再検査で確認できるのは push 済みのコミットのみです。

データエンジニアリングの観点で最も関連が深いのは結果のデータモデルです。形式の異なるツールの出力を 1つのスキーマに正規化すること、安定したフィンガープリントを付与すること、欠損したデータを黙って成功扱いにせず「確認不可」という状態を明示することを重視しました。
