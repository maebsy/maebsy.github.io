## 概要

会員・映画・ジャンル・レビューからなる小規模な映画レビューサービスをモデル化し、決められた問いに SQL で答える学習課題です。必須のクエリに加えて、結果の再現性を確保しました。スクリプトがデータベースを作り直してすべての結果ファイルを書き出し、コミット済みの結果が SQL の出力と一致しなくなった場合は CI が失敗します。

## 背景と課題

課題の要件は、スキーマ、サンプルデータ、そして基本的な検索・結合・集計・サブクエリ・更新・インデックスにわたる 15本のクエリでした。この種の課題でよくある問題は、手作業で貼り付けた結果ファイルが、いつの間にか SQL と食い違ってしまうことです。各結果がすぐ隣にあるクエリから得られたものであることを、リポジトリ自体で示せるようにしたいと考えました。

## 構成

```text
sql/01_schema.sql ─▶ sql/02_seed.sql ─▶ sql/03_queries.sql（Q01〜Q17）
        │                                   │
        └──── scripts/run_all.py ───────────┴─▶ results/*.txt
                     └── --check：一時 DB で実行し、コミット済みの結果と照合（CI）
```

テーブルは `genre`、`member`、`movie`、`review` の 4つです。`review` は会員と映画をつなぐテーブルで、2つの 1対多の関係によって多対多の関係を表しています。サンプルデータはジャンル 10件、会員 15件、映画 22件、レビュー 78件で、親テーブルから子テーブルの順に 1つのトランザクションで投入します。

## 設計・実装の判断

**データの正しさは制約で担保。** 主キー、3つの外部キー、`NOT NULL`、`UNIQUE`、`CHECK` 制約でルールを表現しています。評価は 1〜5、会員の状態は 3種類のいずれか、そして `UNIQUE(member_id, movie_id)` により、1人の会員が 1本の映画に書けるレビューは 1件までです。

**削除時の動作は関係ごとに選択。** 映画から参照されているジャンルの削除は拒否し（`RESTRICT`）、会員や映画を削除した場合はそのレビューも削除します（`CASCADE`）。Q16 でカスケード削除を確認しています。

**DATE 型のないデータベースで正しい日付だけを許可。** SQLite は日付をテキストとして保存するため、`2024-02-30` のような誤りも受け入れてしまいます。そこで日付の各列に `CHECK (date(x, '+0 days') IS x)` を設定し、有効な ISO-8601 形式の日付だけが通るようにしました。

**SQLite では外部キー制約が既定で無効。** すべての SQL ファイルの先頭で `PRAGMA foreign_keys = ON;` を実行し、整合性のシナリオ（B07〜B14）で各制約が不正な入力を拒否することを示しています。

**クエリの範囲。** 内部結合と外部結合（レビューを書いていない会員の抽出を含む）、レビュー数の下限を `HAVING` で指定した上位 5件、`strftime` による月別の推移、そして「ジャンルごとに評価が最も高い映画」を求める CTE と相関サブクエリを扱っています。必須の 15本以外の 2本は追加分として区別し、必須分が要求されたカテゴリと正確に一致しているかをテストで確認しています。

## 担当範囲

スキーマ、サンプルデータ、クエリ、結果生成スクリプト、テスト、ベンチマーク用スクリプト、CI、ドキュメントまで、リポジトリのすべてを 1人で担当しました。

## 検証と成果

- **テスト。** `python -m unittest discover -s tests -t .` → **15件成功**（2026年11月25日に再実行、Python 3.12・Windows）。
- **結果の再現性。** `python scripts/run_all.py --check` → **結果ファイル 33件が再実行結果と一致**。実行計画を含む 3ファイルは、SQLite のバージョンによって表記が変わるため比較から除外しています。
- **CI。** GitHub Actions で、Ubuntu・Windows と Python 3.10・3.13・3.14 の組み合わせで、テストと結果の照合を実行しています。
- **インデックスのベンチマーク**（`scripts/bench_index.py`、測定環境：Python 3.14.4、SQLite 3.46.1）。レビュー 200,078件での結果です。

| クエリ | インデックスなし | `idx_review_movie_id` あり |
| --- | --- | --- |
| 映画 1本のレビュー取得（`WHERE movie_id = ?`） | 9.93 ms | 0.58 ms（17倍高速） |
| 映画ごとの平均（`JOIN` + `GROUP BY`） | 113.72 ms | 231.93 ms（約 2倍遅い） |

このプロジェクトで最も学びが大きかったのは 2行目の結果です。インデックスがある場合、プランナは `movie` を走査し、映画ごとにインデックス経由で `review` を参照する計画に切り替えました。これは、`review` を 1回順に走査して一時 B-tree でグループ化するよりも遅くなりました。インデックスは絞り込みの強い検索には有効ですが、その列を使うすべてのクエリを速くするわけではありません。処理時間は実行環境によって異なるため、実行計画もあわせて記録しています。

## 再現手順

必要なのは Python 3.10 以上のみです（`sqlite3` モジュールは標準ライブラリに含まれています）。

```bash
git clone https://github.com/maebsy/movie-review-db.git
cd movie-review-db
python scripts/run_all.py          # movie_review.db を作成し results/ を書き出す
python scripts/run_all.py --check  # 書き込まずに照合のみ
```

## 制約と改善点

- データは小規模な架空のもので、データ量ではなくモデリングと SQL を示すためのものです。
- 単一ファイルの SQLite データベースで、データの取り込み工程はありません。次の段階としては、外部データセットの取り込み、取り込み時のデータ品質チェックの追加、列指向エンジンでの同じクエリの比較などが考えられます。
