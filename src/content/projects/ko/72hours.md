## 개요

72hours는 코디세이 AI 해커톤 2026에서 5인 팀이 나흘 동안 만든 서비스입니다. AI 코딩 도구로 작은 서비스를 빠르게 만들지만 보안 검토에는 익숙하지 않은 개발자를 대상으로 합니다. 공개 GitHub 주소를 넣으면 여러 스캐너를 실행해 결과를 정규화하고, 로컬에서 서빙하는 LLM이 항목마다 설명을 붙입니다. 검토를 통과한 수정 지시는 MCP로 사용자의 코딩 에이전트에 넘기고, 사용자가 수정을 push하면 다시 검사합니다.

이 페이지는 제가 만든 부분을 중심으로 설명합니다. 팀원의 작업은 제 작업과 맞닿는 곳에 표시했습니다.

## 배경과 문제

AI 도구로 만든 코드에는 DB 관리자 키가 소스에 들어 있거나, 로그인 확인 없는 쓰기 API가 있거나, RLS를 켜지 않은 테이블이 있는 경우가 많습니다. 이런 개발자도 스캐너는 돌릴 수 있지만, 경고가 너무 많아 무엇부터 할지 모르고, 고치는 방법을 모르고, 고친 뒤 정말 해결됐는지 확인할 방법이 없다는 세 가지 문제에 부딪힙니다.

대회 기간의 제약은 다음과 같았습니다.

- 추론용 GPU는 L4 한 장이라 항목당 LLM 처리에 몇 분이 걸립니다.
- 위험도와 셸 명령은 재현 가능해야 하므로 언어 모델이 정하지 않습니다.
- 서비스가 사용자 코드를 직접 수정하지 않습니다. 수정은 사용자 환경에서 사용자의 허락을 받아 이뤄집니다.

## 구조

```text
브라우저 ── Next.js ── FastAPI ──┬── 검사 엔진 ── Opengrep / OSV-Scanner / Gitleaks / 설정 검사
                                 ├── LLM 파이프라인 (vLLM, Qwen3.8-27B): 문맥 분석 → Blue → Red
                                 └── 실행 검증 샌드박스 (Docker, 데모 앱 전용)
사용자 코딩 에이전트 ── 원격 MCP 서버 ── FastAPI
```

저장소 README의 구조도를 따랐습니다. 검사 엔진은 검사 한 번에 JSON 하나를 만들고, LLM 파이프라인이 이를 입력으로 받습니다. MCP 서버는 검사 결과와 승인된 수정 지시를 Claude Code, Codex 같은 에이전트에 제공합니다.

## 구현과 설계 판단

**여러 스캐너의 결과를 하나의 형식으로.** 스캐너마다 출력 형식이 다릅니다. 엔진은 스캐너를 동시에 실행하고, 모든 결과를 공통 스키마로 바꾼 뒤, 줄 번호와 무관한 지문을 붙입니다. 그래서 수정으로 코드 위치가 바뀌어도 같은 문제로 인식합니다. 두 번의 검사를 비교하면 새로 생김, 계속 있음, 해결됨, 확인 불가의 네 상태로 나뉩니다. '확인 불가'를 둔 이유는 스캐너 실패를 '해결'로 잘못 보고하지 않기 위해서입니다.

**판정은 코드, 설명은 모델.** 위험도는 문맥 신호와 위협 정보(CISA KEV, FIRST EPSS)에 CISA SSVC 결정표를 적용하는 코드가 정합니다. 셸 명령도 OS별로 검증한 템플릿에서만 만듭니다. 모델은 설명과 수정 지시만 씁니다. 같은 입력이면 같은 우선순위가 나오고, 모델이 없는 명령을 지어내지 않습니다.

**Blue가 쓰고 Red가 검토.** Blue가 설명과 수정 지시를 쓰면, Red가 우회 가능성·기능 손상·누락을 검토합니다. 재작성 횟수에는 상한이 있고, 통과하지 못한 항목은 수동 확인으로 표시합니다. Red의 pass는 모델의 판단일 뿐 증명이 아닙니다. 공격이 실제로 막히는지는 데모 앱에서만 돌리는 별도의 실행 검증에서만 판정합니다.

**수정은 서버가 아니라 MCP로.** MCP 서버는 Red 검토를 통과하고 최신 검사 결과의 지문과 일치하는 수정 지시만 전달합니다. 검증이 진행 중일 때 같은 요청이 다시 들어오면 중복 접수하지 않습니다. 코드는 사용자의 에이전트가 로컬에서 고치고, push 여부는 사용자가 정합니다.

**요청이 유실되지 않도록 한 배포.** `main` 자동 배포를 구성하고, 작업 대기열, 진행 중 작업 drain, 중단된 릴리스의 다음 실행 시 복구를 넣었습니다.

## 검증과 결과

아래 결과는 저장소에 기록된 것이며, 적힌 대상에만 해당합니다.

- **데모 저장소 1개의 탐지 결과.** 시연용으로 일부러 취약하게 만든 사이트(키는 모두 가짜) [`cafe-order-demo`](https://github.com/maebsy/cafe-order-demo)의 정답지 대비 탐지 15, 미탐 1, 오탐 0. 놓친 것은 `// nosemgrep` 주석으로 숨긴 SQL 인젝션입니다. 일반적인 탐지율이 아닙니다.
- **데모 앱의 수정 전·후 실행 검증.** SQL 인젝션과 반사형 XSS가 수정 전에는 성공하고 수정 후에는 차단됐습니다. 기능 테스트는 전·후 모두 통과했고, 샌드박스 격리 4항목도 확인했습니다(로컬 Docker, 2026-10-31).
- **리뷰로 실제 버그 발견.** #141에서 리뷰어가 검증 도구를 진행 중에 다시 부르면 작업이 중복 접수되는 문제와, 다른 PR과 합쳐질 때 생기는 `TypeError`를 재현했습니다. 둘 다 회귀 테스트와 함께 고친 뒤 머지했습니다.
- **CI.** 관련 파일이 바뀐 PR마다 백엔드, 프론트엔드, 검사 엔진(실제 스캐너 실행), MCP, 배포 테스트를 GitHub Actions로 실행했습니다.

## 재현 방법

저장소 README에 Docker 없이 로컬에서 실행하는 방법이 있습니다. Python 3.12, Node.js 24, 스캐너 3종이 필요하고, 선택으로 vLLM과 24GB급 GPU를 씁니다. GPU가 없어도 엔진 결과와 규칙 기반 설명은 동작합니다.

```bash
git clone https://github.com/maebsy/YMCA-hackathon-2026.git
cd YMCA-hackathon-2026
cp .env.example .env
python -m security_engine doctor   # 설치된 스캐너 확인
```

대회 기간에 쓴 공개 데모 주소는 현재 운영하지 않습니다(2026-11-25 확인).

## 한계와 다음 단계

- 공개 저장소의 기본 브랜치만 검사하고, 비밀값은 현재 파일만 보며 Git 기록은 보지 않습니다.
- L4 GPU 한 장으로는 항목당 몇 분이 걸려 위험도 상위 5건만 LLM으로 분석합니다.
- 실행 검증은 데모 앱만 지원하며 사용자 저장소는 지원하지 않습니다.
- 재검사는 push된 커밋만 볼 수 있습니다.

데이터 엔지니어링 관점에서 가장 관련이 깊은 부분은 결과 데이터 모델입니다. 형식이 다른 도구 출력을 하나의 스키마로 정규화하고, 안정적인 지문을 붙이고, 빠진 데이터를 조용히 성공으로 처리하지 않도록 '확인 불가' 상태를 명시했습니다.
